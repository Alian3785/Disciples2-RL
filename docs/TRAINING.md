# Запуск, обучение и проверка

[Документация проекта](../README.md#documentation)

<a id="setup"></a>
## Окружение и ручная игра

Рабочая среда — Windows с WSL2 Ubuntu 24.04 либо Linux с NVIDIA GPU. Из корня checkout в WSL:

```bash
bash scripts/install_runtime.sh
bash scripts/run_gpu.sh serve_number_grid.py --map trade_train --port 8769
```

Windows-обёртка: `open-numbergrid.cmd -Map trade_train`. Страница — http://127.0.0.1:8769/viewer.html. Параметр `--model results/RUN` подключает совместимую готовую модель; карта должна совпадать с сохранённой. Один сервер обслуживает выбранную карту.

`scripts/run_gpu.sh` выбирает виртуальное окружение CUDA, устанавливает пути проекта и требует GPU. CPU-fallback для обучения и тестов не используется. Путь окружения можно задать через `NUMBERGRID_VENV`.

<a id="training"></a>
## Целевое обучение

Запускать обучение только по запросу пользователя, с указанным им бюджетом. Пример для разрешённого запуска на 50 млн переходов:

```bash
bash scripts/run_gpu.sh benchmark_number_grid.py \
  --map trade_train --seed 42 --total-timesteps 50000000 \
  --checkpoint-interval 5000000 --summary-interval 1000000 \
  --no-episode-reports --tracking auto --output results/RUN
```

Каталог `--output` должен быть новым или пустым. Бюджет — сумма переходов всех параллельных сред. Один переход включает решение агента и автоматические ответы среды до следующего решения.

Перед запрошенным обучением проверяется корректность и проходимость карты; действия проверочного планировщика не передаются агенту. Исключение: `bethrezens_retreat` перед обучением не проверяется без отдельной прямой просьбы пользователя.

Чекпойнты сохраняются каждые 5 млн переходов и на последнем шаге: веса и полное состояние learner. Метрики пишутся каждые 1 млн. Подробные эпизоды выключены; `--episode-reports`, `--evaluate` и `--select-best` требуют отдельного запроса.

`--warm-start PATH` продолжает из сохранённых весов, проверяя карту, конфигурацию и исходники. `--total-timesteps` в этом режиме — общий целевой счётчик. Оптимизатор и текущие партии сбрасываются; наличие файла полного состояния не означает, что этот флаг его восстанавливает.

<a id="artifacts"></a>
## Где смотреть результаты

- `status.json` — текущая фаза и последняя сводка; завершение подтверждается также кодом выхода процесса.
- `results.json` — итог, длительности, параметры и проверенный хеш весов.
- `charts.jsonl`, `metrics.csv` — сохранённые метрики; `tracking.json → url` — графики конкретного запуска.
- `config.json`, `map.json`, `source_hashes.json`, `packages.txt` — условия воспроизводимости.
- `params.msgpack`, `learner_state.msgpack`, `checkpoints/` и `checkpoints.json` — финальные и промежуточные сохранения.

Результаты запусков хранятся в `results/`. Доли побед во время обучения не подменяют отдельную оценку готовой политики. Изменение правил, карты, наблюдений или действий требует проверки совместимости модели.

Для нового проекта Comet можно задать `NUMBERGRID_COMET_VIEW_SCOPE` равным
имени проекта: суффикс отделяет его сохранённые виды от одноимённых видов
других проектов workspace. При таком scope поиск включает виды workspace,
чтобы следующие эксперименты переиспользовали созданный вид. Общий вид и
вид Мизраэля остаются раздельными; правила среды и параметры PPO не меняются.

<a id="observation-day"></a>
## Номер дня в наблюдении

На всех картах Disciples II последний элемент вектора наблюдения —
`state.day / 100.0` (запрос пользователя от 29.10.2026). День начинается с 1:
первое наблюдение содержит `0.01`, после завершения дня через `REST` — `0.02`.
Признак доступен на глобальной карте и в бою; передвижение и боевые раунды
не увеличивают день. Значение не обрезается: день 101 кодируется как `1.01`.
При автоматическом сбросе эпизода новое наблюдение снова содержит `0.01`,
а сохранённое конечное наблюдение — день завершившегося эпизода.

Вход каждой кампании увеличился на один элемент: Default — 2662,
Default Blue Dragon — 2738, Super Last Stand — 1769. Остальные признаки
сохранили свои абсолютные индексы. Старые веса с прежней размерностью входа
несовместимы; для нового наблюдения требуется новое обучение.
Числовой прототип NumberGrid без стратегических дней к картам Disciples II
не относится и этого признака не получает.

<a id="performance"></a>
## Как измерять скорость

Замеры выполняются только по отдельному запросу. Сравниваются одинаковые GPU, версии, seed, бюджет, карта и PPO, без конкурирующих GPU-задач. Для тестового обучения используется `--test-run`; предел — 1 млн переходов суммарно на запуск, без обхода лимита цепочкой продолжений.

`training_seconds` — сумма синхронизированных вызовов learner, включая сбор траекторий и PPO. `ppo_compile_seconds`, `tracking_init_seconds`, `tracking_logging_seconds`, `checkpoint_seconds` и `intermediate_checkpoint_seconds` считаются отдельно. `total_runner_seconds` включает подготовку внутри runner; внешнее время запуска процесса дополнительно включает импорты, запуск WSL и завершение логирования. Вложенные таймеры нельзя складывать повторно.

Принятые ограничения реализации:

- Автоматические бои и ответы противника остаются внутри одного решения агента. Их число влияет на время миллиона решений.
- В пакетных циклах JAX длительность определяется в том числе самой долгой средой. Разные траектории, призывы, параличи и отступления могут давать разную скорость при одинаковом коде.
- Для сравнения вычислений полезна фиксированная нагрузка с одинаковыми состояниями, весами и PRNG. Одинаковый seed обучения не гарантирует побитово одинаковые траектории после изменения компиляции.
- Не менять награды, PPO, отчётность или глобальные XLA-флаги ради красивого сравнения. При измеренном снижении скорости от 7% сообщать условия и величину.
- Помощники `stoix/envs/number_grid_updates.py` сохраняют семантику индексных операций. Поиск пути бота Mirror Match описан в [правилах карты](MIRROR_MATCH.md).

<a id="testing"></a>
## Проверки

Тесты механик, регрессии, обучение и замеры запускаются только по прямому запросу пользователя. При работе над документацией достаточно статической проверки ссылок и diff.

Полный обязательный набор запускается одним CUDA-процессом:

```bash
bash scripts/run_gpu.sh scripts/test_gpu.py --output results/gpu-tests/RUN
```

Windows-обёртка — `run-tests-gpu.cmd`. Общий лимит — 600 секунд с запуском, подготовкой и компиляцией; расширенные проверки без `core` выполняются адресно. Постоянный кеш компиляции ускоряет подготовку, но не пропускает исполнение тестов. `--cold-cache` используется только для отдельного запрошенного замера. На CI без GPU выполняется статическая проверка Ruff.

Исходные механики сверяются с установленной игрой и Python-референсом согласно [AGENTS.md](../AGENTS.md). При переносе тестов сопоставляются смысл действий и одинаковые случайные броски, а не числовые индексы или один seed разных генераторов. Ожидаемые результаты должны быть независимы от проверяемой JAX-реализации. Различия с референсом записываются явно. Chex-проверки форм, конечности и scalar/JIT/vmap дополняют предметные сценарии, но не доказывают правила игры сами по себе.

<a id="metrics"></a>
## Метрики обучения и графики кампании

JAX измеряет игровые показатели из
`C:/Disciples 2 python reference/Big_map/train_campaign.py`, класс
`CampaignMetricsCallback`, методы `_consume_*` и `_build_log_payload`.
Полный набор референсных имён `campaign/...` сохраняется локально и в W&B;
в Comet отправляется компактный набор без дублирующих графиков. Вид графиков
W&B использует тот же каталог разделов, метрик и русских названий.
В Comet состав `campaign` дополнительно зависит от цели карты.
Выбор сервиса сохраняет действующие правила `--tracking auto`.

<a id="metrics-компактный-вид-comet-и-wb"></a>
### Компактный вид Comet и W&B

Первым раскрыт раздел **rollout**. Средняя награда `rollout/ep_rew_mean`
показана слева (в Comet — крупнее), справа — средняя длина эпизода. Оба графика
используют последние 100 завершённых эпизодов, ось X — решения агента:
`training_steps` в W&B, `step` в Comet.

Все графики раздела **campaign** имеют русские названия. Подписи различают
показатели с начала обучения, за последний интервал и за последние 100 эпизодов.
Технические ключи метрик сохраняются; перевод задан в `CHART_TITLES` файла
`numbergrid_comet_dashboard.py`. Оттуда же W&B берёт порядок разделов и графиков.

Следующий раздел **campaign** содержит 35 общих графиков и ещё 14 для карты
с целью `campaign_objective="capital_guardian"` (Мизраэль). По запросу
пользователя от 2026-10-23 графики Мизраэля скрыты на остальных картах:
наличие Мизраэля на карте без цели победить его не включает панели.
Общий сохранённый вид Comet — `Disciples II`, вид для цели Мизраэль —
`Disciples II — Мизраэль`. Шаблоны общие для запусков проекта, поэтому
раздельные имена не дают следующему обучению изменить набор панелей у другой
карты. Ссылка в `tracking.json` выбирает нужный вид. В Comet также не
отправляются метрики этих 14 панелей для других целей; локальные исходные
метрики сохраняются. W&B продолжает использовать полный каталог.

Первый ряд (по запросу
пользователя 14 октября 2026): доли побед и поражений на карте с начала обучения
и доля побед на карте за последний интервал. Доля завершений по лимиту шагов
перенесена ниже, к остальным графикам раздела.

- 25 средних `campaign/completed/*_mean` — для остальных игровых событий:
  бои, развитие, лечение, экономика, магия, призывы, боевые предметы,
  перестановки, уничтоженные отряды, захваченные города,
  а также шесть показателей боя с Мизраэлем: защитные эффекты и эффекты
  постоянного HP, новые раунды, вступления
  в бой, сила армии при первом входе и бонус +10 за бой после 70+ побед
  ([Default](DEFAULT_MAP.md)).
  Количество проданных вещей убрано из вида; выручка от продажи сохранена.
- Четыре общие доли: победы, поражения и тайм-ауты на карте, победы в боях.
- Десять общих `campaign/window/*`: доля побед на карте и в боях за последний интервал
  логирования; среднее число побед в боях, улучшений юнитов, полученного опыта,
  пройденных волн и доля эпизодов с достижением дракона за последние 100 завершённых
  эпизодов, а также найм всех бойцов, найм наёмников и использование зелий за то же окно.
- Восемь `campaign/window/capital_*` за последние 100 эпизодов: полученные
  зелья защиты, HP, точности и инициативы (за каждое +3), доля дошедших до
  Мизраэля, средние только по дошедшим —
  защитные эффекты, эффекты HP, новые раунды и сила армии при первом входе, —
  среднее число побед над отрядами бота Империи на эпизод и наибольшее число
  Инкубов в отряде за эпизод.
- `campaign/victories_total`: общее число побед на карте с начала запуска.
  Каждая успешная кампания считается один раз; победы в отдельных боях не
  увеличивают этот счётчик сами по себе.
- `campaign/mean_seconds_per_million_steps`: среднее число секунд на 1 млн
  переходов всех сред с начала текущего запуска. Формула:
  `training_seconds * 1_000_000 / session_training_steps`. Это время
  синхронизированных вызовов learner (сбор траекторий и PPO), без компиляции,
  оценки, логирования и сохранения. При продолжении из весов учитываются только
  шаги и время новой сессии. Точка записывается вместе с обычной сводкой, включая
  последний неполный интервал; размер блоков learner не меняется.

Подробные [отчёты эпизодов](#episodes) по умолчанию отключены. Только
по прямому запросу с `--episode-reports` при обучении они обрабатываются
отдельным CPU-процессом. В `results.json` затраты главного процесса
(`episode_report_seconds`) и работа фонового процесса (`episode_report_worker_seconds`)
разделены: фоновая работа пересекается с learner и не суммируется с ним.
Полное время цикла включает ожидание окончательной записи отчётов; ожидание
очереди и завершения также сохраняется отдельными полями.

По запросу от 2026-10-27 графики найма и использования зелий показывают последние
100 завершённых эпизодов вместо среднего за весь запуск. Для полученных зелий
защиты, HP, точности и инициативы остаётся один уже существующий график
`campaign/window/capital_defense_acquired_mean`; его накопительный дубликат убран.
До первых 100 завершений средние считаются по имеющимся эпизодам. Полные исходные
ряды остаются в `charts.jsonl` и W&B; Comet отправляет выбранные ряды. Среда,
награды, сбор счётчиков на GPU и интервал логирования 1 млн переходов не меняются.

По запросу от 2026-10-28 график «Побед в боях — в среднем на эпизод» заменён
на «Побед в боях на эпизод — последние 100 эпизодов»
(`campaign/window/battle_victories_mean`). Существующая панель с этим окном
перенесена на место прежнего графика; второй копии нет. Среднее за весь запуск
остаётся в исходных данных, но в сохранённом виде не показывается.

График волн добавлен по запросу пользователя от 2026-10-23. Волна считается
пройденной, когда все её отряды с одинаковым положительным `wave_index` уже
появились и уничтожены. Определение соответствует `ScenarioRules.wave_bonus`
и `maps/super_last_stand.json`: 11 волн по три отряда. Начальные нейтралы,
будущие волны и частично уничтоженные волны не учитываются; каждое завершение
считается один раз, в том числе на последнем шаге победного эпизода.
Счётчик вычисляется на JAX/GPU до auto-reset и работает без отчётов эпизодов.
Среднее берётся по последним 100 завершениям, независимо от исхода; до первых
100 — по имеющимся эпизодам, до первого завершения точки нет. Диапазон Last
Stand — 0–11: это среднее на эпизод, а не сумма за 100 эпизодов.
Ряд отправляется только для карт с `campaign_objective="waves"` и появляется
в будущих обучениях; по старым агрегатам боёв его восстановить нельзя.
Проверки добавлены в существующие
`test_wave_bonus_requires_every_member_and_is_paid_once` и
`test_gpu_reduction_keeps_every_total_and_latest_100_completions`;
запускать их только по отдельному прямому запросу.

Наёмник считается при успешном действии найма с признаком `RecruitmentRules.mercenary`.
Начальный отряд, найм фракционных бойцов в столице или городе, призывы,
воскрешение, увольнение и недопустимые попытки не увеличивают счётчик.
Увольнение или гибель наёмника позднее в эпизоде не отменяют состоявшийся найм.
Общий график `hired_units` по-прежнему включает оба вида найма.
Проверки счётчика добавлены в существующие тесты найма, агрегации и отправки
метрик; их запуск требует отдельного запроса по правилам проекта.

«Обучений у тренера — в среднем на эпизод» считает каждое успешное действие
обучения одного бойца как одну покупку, независимо от количества полученного XP.
Обучение трёх бойцов за один визит даёт три события. Недопустимые попытки,
простой подход к тренеру и боевой опыт не учитываются. Источник определения —
`SiteRules.available/apply` и прямой запрос пользователя; правила покупки опыта
не меняются. Счётчик работает на JAX/GPU, а среднее включает только завершённые
эпизоды. На карте без тренера счётчик равен нулю. График включён для будущих
запусков; в уже работающий `trade-train-44m-hp-20261013` он не добавлялся.
Проверки добавлены в существующие тесты тренера, агрегации и логирования;
без отдельного запроса они не запускались.

Покупка у торговца считается по расходу его запаса: каждая успешная покупка
эликсира или предмета уменьшает `merchant_stock` ровно на единицу, а другие
правила этот запас не меняют. Недопустимые попытки, продажа, обучение у тренера
и покупка заклинаний в лавке не учитываются. На картах без торговцев (например,
Mirror match) счётчик равен нулю. Доля эпизодов с покупкой —
`campaign/merchant_purchase_episodes_rate`. Проверки добавлены в
`number_grid_sites_test.py` и `number_grid_tracking_test.py`; без отдельного
запроса они не запускались. Уже записанные запуски этого ряда не содержат.

Для достижения дракона учитывается вход в бой до автоматического ответа
противника, даже если отряд сразу погиб. Повторные атаки в одном эпизоде
не увеличивают долю; атаки отдельным призывом и заклинаниями с карты не
считаются достижением основным отрядом. Цель берётся из `objective_enemy`
в режимах `dragon` и `blue_dragon`; на картах с другой целью счётчик равен нулю.
При наличии менее 100 завершённых эпизодов используются все доступные;
до первого завершения точка доли не записывается.

Использование эликсиров определяется по допустимому выполненному действию:
все зелья на карте и четыре вида боевых зелий из общего запаса. Покупка,
экипировка, повтор недопустимого действия, сферы и заряды талисманов не
считаются выпитой дозой. Счётчик не зависит от изменения запаса за весь шаг:
добыча после боя может пополнить только что использованное зелье.

Comet получает именованное представление **Disciples II** при создании
эксперимента через API сохранённых представлений (`View`, формат v2 / panels
version 5 SDK 3.58.8). Ссылки в консоли и `tracking.json → url` содержат
`viewId` и сразу открывают этот вид. По прежней ссылке без `viewId` Comet может
показать старый личный черновик; в этом случае выберите **Disciples II** в меню
представлений. REST API Comet не позволяет перезаписать этот личный черновик.
Успех настройки или причина ошибки записывается в `tracking.json → dashboard`.
Ошибка настройки вида не останавливает обучение и запись метрик.

W&B получает такой же сохранённый вид проекта **Disciples II** через W&B
Workspace API (`wandb-workspaces` 0.4.13, `numbergrid_wandb_dashboard.py`).
Ключ вида постоянный (`?nw=disciplesii`), поэтому запуски обновляют один вид,
а не создают копии. Каждый онлайн-запуск пересоздаёт разделы rollout и
campaign; остальные разделы, фильтры и настройки таблицы запусков сохраняются,
технические разделы добавляются только в новый вид. Автоматические панели для
прочих ключей отключены, как в Comet. Все панели — линейные графики по
`training_steps` без сглаживания; в разделе три колонки и столько строк на
страницу, чтобы раздел помещался на одну страницу. Ссылка `tracking.json → url`
открывает вид; ссылка на страницу запуска не записывается (запрос пользователя
от 17.10.2026), страница остаётся в `url` только если вид создать не удалось.
В `tracking.json → dashboard`
записывается `created` или `updated`, `failed` с причиной, а для офлайн-записи —
`not_created` с командой `after_sync`, создающей вид после `wandb sync`.
Ключи выбора лучшей точки `selection/*` и `best/*` в W&B тоже используют ось
`training_steps`. Частота записи одинакова для обоих сервисов: одна сводка на
1 млн решений и последняя неполная сводка.

Полный набор рядов кампании сохраняется в `charts.jsonl`, итоговые значения —
в `results.json → campaign_metrics`; существующие облачные данные не удаляются.
Новые события считаются на JAX/GPU; награды и настройки PPO не меняются.
Изменение применяется к новым запускам: уже работающий процесс обучения
не подхватывает новые счётчики и шаблон графиков автоматически. Историю
использования эликсиров и достижения дракона старых запусков восстановить
из прежних агрегированных счётчиков нельзя.

<a id="metrics-какие-показатели-доступны"></a>
### Какие показатели доступны

| Группа | Показатели |
|---|---|
| Кампания | Завершённые эпизоды, победы, поражения, тайм-ауты; общие и интервальные доли исходов; лучший интервальный процент побед |
| Бои | Победы, поражения и отступления; доля побед; победы на эпизод; уникальные уничтоженные отряды, включая убийства заклинаниями |
| Развитие и экономика | Улучшения юнитов после боя, число обучений у тренера, строительство, сундуки, зачищенные руины, покупки у торговца, проданные предметы и выручка |
| Восстановление | Число успешных платных лечений в столице и восстановленные HP; использованные дозы эликсиров на карте и в бою |
| Магия | Выученные и купленные заклинания; успешные применения, включая свитки и посохи; призванные на карте существа |
| Отряд | Все нанятые юниты и отдельно наёмники из лагерей, экипировка боевых предметов, расход предметов и зарядов, перестановки |
| Цель карты | Захваченные города; достижение целевого дракона основным отрядом в драконьих режимах |
| PPO | Policy/value loss, энтропия, approximate KL, clip fraction и explained variance |
| Оценка модели | Награда, длина и доля побед отдельно для детерминированного и случайного выбора действий |

Для действий доступны суммарные счётчики `campaign/<показатель>_total`,
средние на эпизод `campaign/<показатель>_per_episode_mean`, оконные средние
`campaign/window/<показатель>_mean`. Доли эпизодов, в которых использовалась
механика, сохраняют имена референса, например `campaign/hire_episodes_rate`,
`campaign/spell_cast_episodes_rate`, `campaign/battle_item_use_episodes_rate`.
Найм, призывы, предметы, перестановки и заклинания, для которых Python строил
дополнительные картинки, представлены также числовыми рядами для графиков.

Сценарный бот столицы в JAX отсутствует. Его три `scripted_bot`-метрики не
заполняются искусственными нулями: причина записывается в
`tracking.json → campaign_metrics.unavailable`. Это изменение логирования
не добавляет самого бота.

<a id="metrics-значение-интервалов-и-знаменателей"></a>
### Значение интервалов и знаменателей

- Сводки отправляются каждые **1 000 000 решений агента** и в конце последнего
  неполного интервала. Размеры rollout, learner-блоков и настройки PPO не меняются.
- `campaign/window/episodes`, доли исходов и `battle_win_rate` относятся ко
  **всему интервалу между сводками**, как `window_*_counter` в референсе.
- `campaign/window/*_mean` относятся к **последним 100 завершённым эпизодам**.
  Окно сохраняется между сводками. Для одновременного завершения эпизодов на
  одной GPU порядок задаётся обновлением PPO, шагом rollout и индексом среды.
- `campaign/window/dragon_reached_episodes_rate` использует это же окно
  последних 100 эпизодов, а не интервал в миллион решений. Числитель —
  количество эпизодов с хотя бы одним боем основного отряда против дракона.
- `enemy_squads_defeated_mean_100` включает все способы уничтожения отрядов,
  но каждый отряд считается один раз. Число образцов выводится отдельно.
- Как в референсе, накопительное `*_per_episode_mean` делит все события,
  включая текущие незавершённые эпизоды, на число завершённых эпизодов.
  Дополнительные `campaign/completed/*_mean` используют только завершённые
  эпизоды; их не следует путать с референсным отношением.
- `*_episodes_rate` — число завершённых эпизодов с хотя бы одним событием,
  делённое на число завершённых эпизодов. Повторные применения не увеличивают
  эту долю выше единицы. Все доли имеют диапазон 0…1.
- При нулевом знаменателе доли и средние опускаются, а счётчики остаются.
  Это предотвращает ложные нулевые точки при отсутствии наблюдений.
- `rollout/ep_rew_mean` и `rollout/ep_len_mean` используют последние 100
  завершённых эпизодов; прежние `episodes/return_mean` и `length_mean` сохраняют
  среднее всего интервала. `eval/deterministic_*` и `eval/stochastic_*`
  являются референсными именами существующих оценок JAX.

Начальная оценка необученной модели не запускается: точки `eval*` на нулевом
шаге нет. Итоговые оценки argmax и выбора по вероятностям по умолчанию тоже
отключены. Они выполняются после обучения только при явном `--evaluate` или
`--select-best` и записываются на последнем шаге обучения. Чекпойнты включены
по умолчанию: веса и полное состояние learner сохраняются каждые 5 млн переходов
и на последнем шаге, без оценки и выбора модели. `--checkpoint-interval` задаёт
этот интервал независимо от сводок Comet/W&B, которые остаются каждые 1 млн.
`--no-save-checkpoints` отключает промежуточные сохранения; финальное остаётся.
Интервал и включение записываются в `config.json` (`checkpointing`), интервал и
время сохранения — в `results.json` (`checkpoint_interval`,
`intermediate_checkpoint_seconds`, `checkpoint_seconds`). Отчёты эпизодов
по-прежнему требуют отдельного явного `--episode-reports`.
В `results.json` без оценки записываются `evaluation_status: "not_requested"`,
`final_evaluation: null`, `sampled_evaluation: null` и нулевые длительности
оценок. Это отсутствие измерения, а не нулевая доля побед. При выполненной
оценке статус — `completed`, поля содержат её результаты и длительности.
Поля `initial_evaluation` и `initial_evaluation_seconds` больше не создаются.

Показатели PPO рассчитываются по данным JAX learner. KL использует
`mean(exp(log_ratio) - 1 - log_ratio)`, clip fraction — долю отношений
вероятностей за пределами `1 ± clip_eps`. Explained variance измеряется по
исходным оценкам ценности и GAE-targets rollout; при нулевой дисперсии targets
используется 0. Новые величины диагностические: функция потерь, градиенты,
семплирование и правила игры не изменены.

<a id="metrics-реализация-и-проверка"></a>
### Реализация и проверка

События вычисляются в `stoix/envs/number_grid_metrics.py`. Сохраняется результат
действия на карте **до** автоматического боя: завершившийся в этом же шаге
призыв не теряет свою статистику. Исходы боёв и улучшения суммируются внутри
автоматического цикла. Поражение призванного существа учитывается как поражение
в бою, но не как поражение кампании.

`NumberGridEpisodeMetrics` хранит счётчики эпизода в JAX-состоянии обёртки.
Терминальное событие включается до сброса. `summarize_campaign` сворачивает
полные счётчики и признаки участия на GPU; для окна передаёт максимум 100
завершённых записей за learner-блок. При большем количестве завершений общие
счётчики не теряются. Обмена с CPU на каждом шаге нет. Наблюдение политики и
совместимость весов этим изменением не затронуты.

Все отправленные точки, включая режим `--tracking disabled`, сохраняются
в `charts.jsonl` каталога запуска. Итоговые значения — `results.json →
campaign_metrics`. Ссылка на облачные графики — `tracking.json → url`.

Обязательные GPU-регрессии: `number_grid_campaign_metrics_test.py` и
`number_grid_tracking_test.py`. Проверяются повтор недопустимого действия,
автоматическая победа от яда, гибель призыва, события перед автоматическим
боем, более 100 завершений, сброс эпизода, знаменатели, обе облачные службы и
локальное сохранение графиков.

По запросу о графиках добавлены проверки успешного расхода эликсиров и
недопустимого повтора в `number_grid_campaign_metrics_test.py`, счётчика
боевых зелий и исключения сфер / экипировки в `number_grid_battle_items_test.py`.
Оконная агрегация проверяет 130 завершений, несколько атак дракона за эпизод,
сохранение последних 100 записей и отсутствие ложной точки до завершений.
`number_grid_tracking_test.py` проверяет новые ряды в Comet и локальном файле,
сохранение выручки, удаление графика количества продаж и обновление шаблона.
Источники определений: пользовательский запрос; существующие допустимые
действия `PotionRules.apply`, `BattleItemRules.use/consume` и результат
`NumberGrid._world_step` до автоматического боя.

Вид W&B проверяет `test_wandb_view_repeats_comet_sections_titles_and_axis`:
те же разделы, метрики, русские названия и раскрытые разделы, что у вида Comet,
ось `training_steps`, все графики раздела на одной странице и обновление
существующего вида с сохранением чужих разделов (без сети: сохранение и чтение
вида подменены). `test_auto_tracking_prefers_reachable_wandb_cloud` проверяет
ссылку на вид и то, что ошибка вида оставляет запуск W&B. Источник требований —
запрос пользователя повторить графики Comet в W&B.

<a id="metrics-подробные-эпизоды"></a>
### Подробные эпизоды

Только при явном `--episode-reports` обучение дополнительно сохраняет [отчёты по каждому завершённому эпизоду](#episodes): конечные формы и уровни, XP бойцов, улучшения, конкретные побеждённые армии и противника при поражении. События собираются на GPU и выгружаются пакетами после learner-блока.

<a id="episodes"></a>
## Подробные отчёты по эпизодам

С 23.10.2026 подробные отчёты по умолчанию **отключены**. Включать их можно
только по прямому запросу пользователя флагом `--episode-reports` для боевых карт
с развитием юнитов. Код обработки сохранён. Без этого флага события отчётов
не собираются на GPU, пакеты не копируются на CPU, фоновый обработчик не запускается
и файлы `episode_reports*` не создаются. `--no-episode-reports` явно оставляет
диагностику отключённой. Агрегированные метрики Comet/W&B и сохранение весов работают
как обычно. Описанные ниже файлы и обработка относятся к явно включённым отчётам.

<a id="episodes-файлы-в-каталоге-запуска"></a>
### Файлы в каталоге запуска

- episode_reports.jsonl.gz — одна JSON-запись на каждый завершённый эпизод,
  gzip-сжатие без потери записей или детализации.
- episode_reports.md — читаемая сводка: частые конечные составы, полученный опыт,
  побеждённые армии и противники, завершившие эпизод поражением.
- episode_reports.summary.json — полная сводка без ограничения числом строк таблицы.
- episode_reports.metadata.json — версия формата, карта, каталог юнитов,
  начальные составы противников и исходные ID из Python-референса.
- episode_reports.partial.json — незавершённые эпизоды на момент остановки
  штатного обучения, по последнему записанному значимому событию. Они не
  считаются завершёнными и не включаются в итоговые средние.

По запросу пользователя от 13.10.2026 отчёт сжимается gzip (уровень 6) и
дописывается **раз в 1 млн переходов**, вместе со сводками, а также в конце
запуска, включая последний неполный интервал. Между этими границами в памяти
накапливаются только сжатые записи текущего интервала. Число полных отчётов
сверяется с числом завершённых эпизодов; расхождение останавливает запуск с ошибкой.
Каждая запись на диск закрывает отдельный gzip-поток, поэтому уже сохранённые
интервалы можно читать во время обучения через `gzip.open(path, 'rt', encoding='utf-8')`.
При аварии последние ещё не выгруженные записи могут потеряться. В сводках и
`results.json:episode_reports` сохраняются `episodes_file_bytes` (фактический
размер файла) и `episodes_uncompressed_bytes` (размер исходных JSON-записей).
Старые `.jsonl` остаются в прежнем формате, если их отдельно не архивировали.

<a id="episodes-содержание-эпизода"></a>
### Содержание эпизода

initial_party и final_party содержат названия, ключи каталога, уровни, текущий XP,
порог следующего уровня и признак жизни каждого занятого места. Порог у начального
снимка не записывается. Погибший боец остаётся в составе до увольнения.

fighter_id уникален внутри эпизода и следует за бойцом при перестановках, включая
перемещение целой колонки крупного существа. Уволенный и вновь нанятый боец одного
типа получают разные ID. fighters сохраняет также историю выбывших бойцов.

Для каждого бойца xp_received — весь начисленный ему опыт в эпизоде,
battle_xp_received — опыт из боёв, trainer_xp_received — опыт тренера.
Это начисление до сброса XP при повышении и до ограничения порогом, если
нужное здание не построено. Текущий xp и начисленный xp_received имеют разный смысл.
experience_events сохраняет источники и величины начислений.

upgrades хранит шаг и день, бойца, старую и новую форму/уровень, полученный XP и
противника. Обычный численный рост уровня тоже попадает в этот журнал, даже если
за него не положена награда продвижения. Одновременные повышения упорядочены по
конечному слоту; между решениями сохраняется временной порядок.

battles содержит завершённые бои с результатом victory, defeat или retreat.
defeated_armies содержит конкретные уничтоженные отряды с номером JAX (с 1),
индексом массива (с 0), исходным reference_id при наличии, составом и уровнями.
Способы уничтожения разделены: hero, summon, spell. Уровни противника берутся из
его сохранённого состояния после боя, включая рост победившего противника.
При timeout или victory поле defeat пустое. При defeat в нём записаны причина
и конкретный противник; проигрыш отдельного призыва не считается гибелью героя.

Временные боевые призывы, копирование и отдельный отряд призыва с карты не
заменяют постоянных бойцов в отчёте. Для них берутся сохранённые собственные
профили и состав основной армии. Постоянная прокачка и найм сохраняются.

<a id="episodes-jax-и-полнота-данных"></a>
### JAX и полнота данных

Источник данных — существующие NumberGrid.step/_battle_step_regular,
Progression.finish, CastingRules.finish_battle и UnitSwapRules.apply.
Награды, наблюдения, допустимые действия, PRNG и обновления PPO не изменяются.

Снимки и признаки событий вычисляются внутри JAX-перехода до autoreset. На GPU
сохраняются только компактные числовые данные, затем значимые события стабильно
упаковываются по порядку update/time/device/batch/environment. Ёмкость упаковки
равна числу переходов блока: ограничения последними 100 эпизодами и переполнения
с потерей записей нет. Один переход завершает максимум один бой; очередь нападений
требует отдельных следующих решений среды.

После блока CPU получает число записей и заполненную часть пакета. Размеры
передаваемых срезов округляются до степени двойки, чтобы переиспользовать их
компиляцию. JSON и названия формируются уже из полученного пакета. CPU-симуляции,
пошаговых обратных вызовов, передачи наблюдений на CPU или действий из отчётности
в политику нет. Объём исходного пакета зависит от размера learner-блока;
сжатый буфер сбрасывается на каждой границе отчётности и не копит весь запуск.
Полный сжатый журнал растёт на диске. Размеры блоков learner и PPO не меняются.

<a id="episodes-параллельная-обработка-при-обучении"></a>
#### Параллельная обработка при обучении

По запросу пользователя от 22.10.2026 `benchmark_number_grid.py` передаёт уже
скопированные на CPU пакеты в `AsyncEpisodeReports`. Отдельный процесс собирает
истории, считает сводки, формирует JSON, сжимает gzip и пишет файлы параллельно
следующему блоку обучения. Он не импортирует JAX и не создаёт контекст CUDA.
Передача с GPU остаётся пакетной после блока; копирование, постановка в очередь
и обычные метрики по-прежнему выполняются в процессе обучения.

Один поток доставки передаёт команды в порядке получения и проверяет ответы
процесса. Очередь ограничена восемью командами плюс одна обрабатываемая команда;
в каждом пакете максимум событий одного learner-блока. Если обработчик отстаёт,
следующая отправка ждёт свободного места. События не отбрасываются и не выбираются
по частоте. Границы сводок остаются прежними — каждый миллион переходов и конец;
локальная сводка может появиться с задержкой фоновой обработки.

После каждого пакета проверяется число завершённых эпизодов. Перед успешным
окончанием запуска очередь полностью обрабатывается, сохраняются последний
интервал и незавершённые эпизоды, сверяются общее число событий и число эпизодов,
ожидается успешное завершение процесса записи. Обрабатываемое исключение learner
тоже дожидается записи принятых пакетов. Ошибки обработчика, нарушенный порядок
или неполные данные завершают обучение ошибкой; причина сохраняется в
`episode_reports.worker.log` и, если запись ещё возможна, в
`episode_reports.failure.json`. При принудительном завершении процессов или
отказе диска сохранность ещё не записанной очереди не гарантируется.

Время сбора событий на устройстве входит во время learner. В `results.json`:

- `episode_report_mode = async_process` обозначает новый режим обучения;
- `episode_report_seconds` — время, затраченное главным процессом на запуск
  обработчика, передачу пакетов, постановку команд в очередь и ожидание завершения;
- `episode_report_worker_seconds` — работа отдельного процесса: сборка историй,
  JSON, сжатие, сводки и запись. Пересекается с обучением и **не прибавляется** к
  времени learner или полному времени запуска;
- `episode_report_queue_wait_seconds` — ожидание места в заполненной очереди;
- `episode_report_drain_seconds` — окончательное ожидание обработки и закрытия;
- `episode_report_startup_seconds` — подготовка процесса записи.

Последние три поля входят в затраты главного процесса; ожидание очереди во время
завершения также входит в `drain_seconds`, поэтому их нельзя просто складывать.
`training_loop_seconds` включает окончательное ожидание записи, а
`total_runner_seconds` — весь runner. В старых запусках без `episode_report_mode`
поле `episode_report_seconds` включало синхронную обработку и запись. Фактическое
ускорение без отдельного замера неизвестно. `report_number_grid.py` сохраняет
синхронную запись диагностических эпизодов.

<a id="episodes-уже-обученная-модель"></a>
### Уже обученная модель

report_number_grid.py проводит новые диагностические эпизоды без обучения и без
изменения весов. Пример из PowerShell для сохранённого Super Last Stand:

    wsl -d Ubuntu-24.04 -u minigrid --cd C:\jaxjax -- bash scripts/run_gpu.sh report_number_grid.py --results results/super_last_stand-20m-20261013 --output results/super_last_stand-20m-20261013-diagnostics --episodes 16 --batch-size 8 --policy argmax

Для случайного выбора действий используется --policy sample. Seed каждого эпизода
зависит от --seed и номера эпизода, поэтому смена размера пакета не меняет потоки
случайных чисел. Диагностика работает только на CUDA, без перехода на CPU.

Это новые эпизоды итоговой модели, а не восстановленная история прошлого обучения.
Стандартные итоговые оценки 1024 эпизодов остаются агрегированными; подробные
диагностические запуски запрашиваются отдельно. На старых запусках подробных
исторических отчётов задним числом не появится.

<a id="episodes-проверки"></a>
### Проверки

Расширенное покрытие: stoix/tests/number_grid_episode_reports_test.py. Проверяет
XP при сбросе на повышении, XP тренера, перестановку целой колонки крупного
существа, пустые пакеты, временные формы, призывы, немедленную победу над
появившейся армией, полноту и порядок пакетов, идентичность при перестановках и
повторном найме, terminal-снимок перед autoreset и неизменность перехода среды.
Также проверяет чтение нескольких gzip-интервалов без потери или дублирования
эпизодов, отсутствие записи между сводками и выгрузку последнего интервала.
Добавлены проверки равенства синхронных и фоновых отчётов, заполненной очереди,
сохранения принятых пакетов при исключении learner, передачи ошибки обработчика,
ошибки окончательной записи, запрета перезаписи существующего журнала
и обнаружения аварийного завершения обработчика. По запросу на доработку от 22.10.2026
тесты и замеры не запускались; выполняются только по отдельному запросу.
Тесты не входят в core; запускаются только по отдельному запросу через run_gpu.sh.
